# sqld-admin

A small web UI and JSON API for managing [libsql/sqld](https://github.com/tursodatabase/libsql)
namespaces: create, adopt, rename, fork, and delete databases, browse table
schemas and rows, and run SQL.

## Architecture

```
Browser (static SPA, HTTP Basic)
   |
   v
sqld-admin (node:http: static files + JSON API)
   |-- user port  : POST /v2/pipeline (Host: <ns>.<SQLD_HOST_SUFFIX>)
   '-- admin port : POST/DELETE /v1/namespaces/...
   v
sqld (namespace mode)
```

The browser never talks to sqld directly. sqld credentials and the admin URL
stay on the server.

## Requirements

- Node.js 22 or newer
- Docker with Compose, to run the full stack locally

## Quick start

1. Create your environment file and sqld credentials:

   ```bash
   cp .env.example .env
   npm run auth:generate
   ```

   `auth:generate` creates `secrets/sqld-jwt-public.pem` and
   `secrets/sqld-jwt-private.pem`, then fills `SQLD_AUTH_TOKEN` and
   `SQLD_ADMIN_TOKEN` in `.env`. Set `ADMIN_USER` / `ADMIN_PASSWORD`, or set
   `ALLOW_NO_AUTH=true` for local-only development.

2. Start the full stack (sqld + the admin UI/API):

   ```bash
   docker compose up -d --build
   ```

   This builds the app image from `Dockerfile` and starts it with the `sqld`
   service on the compose network. The app is published on port 3000; sqld's
   user and admin ports are published on 18080/18081 for debugging.

3. Open <http://localhost:3000>. The browser prompts for the HTTP Basic
   credentials from `ADMIN_USER` / `ADMIN_PASSWORD` (or use `ALLOW_NO_AUTH=true`
   for local-only development).

Stop the stack with:

```bash
docker compose down
```

To run the app on the host against the Dockerized `sqld`:

```bash
docker compose up -d sqld
SQLD_URL=http://127.0.0.1:18080 \
SQLD_ADMIN_URL=http://127.0.0.1:18081 \
node --env-file-if-exists=.env server.js
```

Stop that sqld service with `docker compose stop sqld`.

To use the alternate `docker-compose.dev.yml` (ports 8080/8081) instead, start
it manually and run the app with matching overrides:

```bash
docker compose -f docker-compose.dev.yml up -d
SQLD_URL=http://127.0.0.1:8080 \
SQLD_ADMIN_URL=http://127.0.0.1:8081 \
node --env-file=.env server.js
```


## Environment variables

| Variable | Default | Description |
| --- | --- | --- |
| `PORT` | `3000` | Port the admin app listens on. |
| `HOST` | `0.0.0.0` | Interface the admin app binds to. |
| `SQLD_URL` | `http://sqld:8080` | sqld user (SQL) endpoint. Host-run development uses `http://127.0.0.1:18080`; `http://sqld:8080` is for container networking. |
| `SQLD_ADMIN_URL` | `http://sqld:8081` | sqld admin (namespace management) endpoint. Host-run development uses `http://127.0.0.1:18081`. |
| `SQLD_HOST_SUFFIX` | `local` | Suffix for the per-namespace `Host` header: `<ns>.<SQLD_HOST_SUFFIX>`. |
| `SQLD_AUTH_TOKEN` | empty | Bearer JWT sent to the sqld user API. Generated by `npm run auth:generate`. |
| `SQLD_ADMIN_TOKEN` | empty | Shared Basic key sent to the sqld admin API. Generated by `npm run auth:generate`. |
| `SQLD_JWT_PRIVATE_KEY_FILE` | `secrets/sqld-jwt-private.pem` | Ed25519 private key used by the token UI. Optional; missing keys disable generation without failing startup. |
| `ADMIN_USER` | none | HTTP Basic username for the app. Required unless `ALLOW_NO_AUTH=true`. |
| `ADMIN_PASSWORD` | none | HTTP Basic password for the app. Required unless `ALLOW_NO_AUTH=true`. |
| `ALLOW_NO_AUTH` | `false` | Bypass app authentication. **Local development only.** |

`SQLD_AUTH_TOKEN` and `SQLD_ADMIN_TOKEN` are sqld server credentials and do not
replace the app's own Basic auth login. When using `docker-compose.yml`, the
`app` service sets `SQLD_URL=http://sqld:8080` and
`SQLD_ADMIN_URL=http://sqld:8082` directly; host-run development uses the
host-published ports.

The app sends `SQLD_AUTH_TOKEN` as `Authorization: Bearer ...` to sqld's user
API and `SQLD_ADMIN_TOKEN` as `Authorization: Basic ...` to sqld's admin API.
sqld verifies the JWT with the public key mounted at
`/run/secrets/sqld-jwt-public.pem` and checks the admin key against
`LIBSQL_ADMIN_AUTH_KEY`.

The suite uses an in-process fake sqld and ephemeral ports, so it does not

## Docker

`docker-compose.yml` includes both services:

- `app` — built from `Dockerfile`, containing `server.js`, `lib/`, and the
  static frontend in `public/`; published on port 3000.
- `sqld` — the libsql server in namespace mode, with its data bind-mounted
  from `./data`.

Start them together:

```bash
docker compose up -d --build
```

The app container connects to `sqld` over the compose network at
`http://sqld:8080` (user API) and `http://sqld:8082` (admin API). The compose
file overrides `SQLD_ADMIN_URL` to port 8082 because that is where the `sqld`
service listens for admin requests. Change the published host ports in
`docker-compose.yml` if 3000/18080/18081 are already in use.

sqld authentication is enabled in the compose stack:

- The public JWT verification key is bind-mounted read-only from
  `./secrets/sqld-jwt-public.pem` and passed as
  `SQLD_AUTH_JWT_KEY_FILE=/run/secrets/sqld-jwt-public.pem`.
- The admin API key comes from `SQLD_ADMIN_TOKEN` via
  `LIBSQL_ADMIN_AUTH_KEY`.
- The app sends the JWT as `Bearer` to the user API and the admin key as
  `Basic` to the admin API.

To rotate the credentials, run `npm run auth:generate -- --force` and restart
the stack. The private key stays in `./secrets/` and is required to mint a new
JWT.

The app container also mounts `./secrets/sqld-jwt-private.pem` read-only at
`/run/secrets/sqld-jwt-private.pem` (`SQLD_JWT_PRIVATE_KEY_FILE`) so the token
UI can sign. It runs as `APP_UID:APP_GID` (written to `.env` by
`npm run auth:generate`) so it can read the host's 0600 private key.

To build or run the app image manually:

```bash
docker build -t sqld-admin .
docker run --rm -p 3000:3000 \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/secrets/sqld-jwt-private.pem:/run/secrets/sqld-jwt-private.pem:ro" \
  -e SQLD_JWT_PRIVATE_KEY_FILE=/run/secrets/sqld-jwt-private.pem \
  -e ADMIN_USER=admin \
  -e ADMIN_PASSWORD=change-me \
  -e SQLD_URL=http://sqld:8080 \
  -e SQLD_ADMIN_URL=http://sqld:8082 \
  -e SQLD_AUTH_TOKEN=<jwt> \
  -e SQLD_ADMIN_TOKEN=<admin-key> \
  sqld-admin
```

The image defaults to the non-root `node` user. The token UI needs a user that
can read the 0600 private key, which is why Compose sets `APP_UID:APP_GID` and
manual runs pass `--user`. The sqld endpoints in `SQLD_URL` / `SQLD_ADMIN_URL`
must be reachable from inside the container, and the sqld instance must be
configured with the matching public key and admin key.

## Token generation

Open <http://localhost:3000/#/auth> (the **Auth** nav item) to mint sqld JWTs
with the same Ed25519 key that signs `SQLD_AUTH_TOKEN`.

- Access: **Read/write** or **Read-only**.
- Database: **All databases** (read/write, full sqld access) or one registered
  database.
- Expiry: 1 hour, 1 day, 7 days, 30 days (default), 90 days, or 1 year.

All databases + read/write produces `{ exp }` and grants full sqld access. A
selected database scopes the token with sqld's `p.rw.ns` / `p.ro.ns` claims.
All-databases read-only is intentionally not offered, because sqld cannot
express it without enumerating every current namespace.

The token is shown once and is never stored by the app; copy it immediately.
Generated tokens are client credentials for their scope and do not replace
`SQLD_AUTH_TOKEN`. There is no per-token revocation: rotate the signing key
with `npm run auth:generate -- --force` and restart the stack. Rotation
invalidates every JWT signed with the old key, including `SQLD_AUTH_TOKEN`.

The UI shows a warning when `ALLOW_NO_AUTH=true`. Set `ADMIN_USER` /
`ADMIN_PASSWORD` and `ALLOW_NO_AUTH=false` before exposing the app.

## Security notes

- **Basic auth on every route**, static and API. Credentials are compared in
  constant time with `crypto.timingSafeEqual` over SHA-256 digests.
- Put the app behind **HTTPS** (a TLS-terminating reverse proxy). Basic auth
  sends credentials with every request and must not travel over plain HTTP.
- **Keep the sqld admin port private.** The admin API can create, fork, and
  delete namespaces. Do not expose it to the internet; only the app needs it.
  `SQLD_ADMIN_TOKEN` is its shared key and must remain server-side.
- **Keep `secrets/sqld-jwt-private.pem` private.** It can mint new JWTs for the
  sqld user API, and the app container mounts it read-only so the token UI can
  sign. Anyone who compromises the app process or its Basic auth can mint
  tokens. `secrets/` is gitignored; back it up only in a secret store, and keep
  app Basic auth enabled.
- **The SQL console is privileged.** It executes arbitrary SQL against the
  selected namespace with the app's sqld credentials.
- `ALLOW_NO_AUTH=true` is for local development only; never use it on a
  shared or public deployment.
- Request hardening: `POST`/`PATCH`/`DELETE` require
  `Content-Type: application/json`; a present `Origin` must match the request
  `Host`; request bodies are limited to 1 MB (413 when exceeded).
- Responses set `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'self'`, and `Cache-Control: no-store`.
- Static files are served only from `public/`; path traversal attempts return
  404.
- Secrets (passwords, tokens, `Authorization` headers) are never logged.

## Verified sqld behavior

The following was checked against the local sqld deployment in namespace mode
(Phase 0):

- `POST /v1/namespaces/spike/create` with `{}` returned `200 {}` **without**
  an auth header on this deployment.
- A request `Host` header selects the namespace: `Host: spike.local` hits
  `spike`. An unknown `Host` (for example `other.local`) returns `404`:

  ```
  { "error": "Namespace `otherNNNN` doesn't exist" }
  ```

- `POST /v2/pipeline` create/select responses include `baton`, `base_url`, and
  extra fields (`replication_index`, `rows_read`, `rows_written`,
  `query_duration_ms`). The documented `results[].response.result` shape still
  holds, and the client ignores the extra fields.
- Forking `spike` to `spike2` returned `200` and copied the `t` table; deleting
  both namespaces returned `200`.

## Known limitations

- Databases created outside the app appear only after using "Add existing".
- Database rename is implemented as fork + delete: it is not atomic and
  temporarily doubles that database's storage.
- The data view is read-only; there is no row editing.
- There is a single shared login, with no per-user permissions.
